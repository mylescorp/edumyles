# Landing Page Blueprint

Use this reference to recreate the EduMyles-style landing page for another SaaS product while changing the market, brand, copy, data, and imagery.

## Page Order

Build the homepage in this order:

1. Hero
2. Trust stats
3. Problem section
4. Modules or platform capabilities
5. Integrations
6. Persona benefits
7. Comparison
8. How it works
9. Brand story or values
10. ROI calculator
11. Testimonial
12. Mobile teaser
13. Pricing
14. Final CTA

This sequence should remain recognizable even when individual section names change.

## Hero

Use a dark, product-specific hero with:

- Clear category headline: "The all-in-one [category] platform for [market]".
- One primary conversion CTA, usually waitlist, start trial, or book demo.
- One secondary CTA, usually pricing, product tour, or contact sales.
- Trust eyebrow tied to the market.
- Three compact dashboard cards on desktop showing key metrics.
- Sample-data labeling when the metrics are illustrative.
- First-viewport brand signal: logo/name and category must be immediately obvious.

Avoid generic decorative illustrations. Use actual product dashboards, live-looking panels, or domain-specific operational previews.

## Trust Stats

Use three to five concise stats:

- Time saved
- Revenue collected or cost recovered
- Workflow completion rate
- Active tenants, teams, customers, or locations
- Support response or implementation timeline

If not yet real, label as pilot, estimate, benchmark, or sample. Do not imply fake traction.

## Problem Section

Use three cards with concrete pain:

- Manual or duplicated workflow
- Scattered data or lack of visibility
- Communication, compliance, payments, or reporting breakdown

Each card should contain an icon, short title, and one sentence. Write for the buyer's daily frustration, not for abstract software categories.

## Modules Section

Source module cards from shared constants where possible. Use a 2-column mobile and 3-column desktop grid. Each card should include:

- Lucide icon
- Module name
- Included/available label
- Outcome-focused description
- Link to features or product tour

For a non-school SaaS, replace modules with domain equivalents. Example for clinic SaaS:

- Patient records
- Scheduling
- Billing
- Claims
- Pharmacy
- Lab orders
- Communications
- Staff management
- Analytics

## Integrations

List tools the buyer already uses:

- Auth and SSO
- Payment rails
- Email/SMS/WhatsApp
- Accounting
- Calendars
- Data import/export
- Government or compliance systems

Use logos only when assets are available and licensing is acceptable. Otherwise use clean text chips or icon labels.

## Persona Benefits

Use tabs, cards, or columns for the main roles:

- Owner/executive/admin
- Operator/staff
- End customer/client

Each role needs specific benefits and workflows. Do not repeat the same feature list with different nouns.

## Comparison

Compare:

- Manual tools
- Generic SaaS or spreadsheets
- The new product

Rows should be operationally meaningful: setup time, reporting, payments, communication history, role permissions, mobile access, auditability, support, and pricing clarity.

## How It Works

Use three steps:

1. Configure tenant, modules, roles, and data imports.
2. Invite team/customer users and connect integrations.
3. Operate daily workflows from dashboards and portals.

Keep the implementation promise believable. Avoid "done in minutes" unless the app truly supports it.

## Brand Story

Include mission, vision, values, or founder story only when it increases trust. For B2B SaaS, keep it brief and practical:

- Why this market needs a dedicated product.
- What operational pain the company understands.
- What principles shape implementation and support.

## ROI Calculator

Tailor inputs to the domain:

- Number of users, customers, locations, assets, or transactions.
- Hours spent on manual work.
- Error/rework rate.
- Monthly revenue leakage or collection delay.
- Staff hourly cost.

Output:

- Estimated hours saved per month.
- Estimated value recovered.
- Payback period against selected pricing plan.

Show assumptions near the calculator. Do not hide the math in copy.

## Testimonial

Use a real testimonial when available. If not, use a clearly non-deceptive placeholder in development branches and replace it before launch. Avoid names, photos, or institution claims that are not real.

## Mobile Teaser

Include when mobile matters:

- Field work
- Parent/customer portal
- Staff notifications
- Offline capture
- Approvals
- Payments

Use a phone frame or actual mobile screenshots. Keep it secondary to the product value.

## Pricing

Use three plans by default:

- Starter for small teams or single location.
- Professional as the featured plan.
- Enterprise for custom networks, SSO, SLA, API, or white-label.

Put plan data in shared constants:

- key
- name
- tagline
- price
- annual price
- limits
- description
- features
- CTA
- href
- featured flag

Use the buyer's currency and billing cadence. Do not leave KES, school limits, or EduMyles feature names unless appropriate.

## Supporting Pages

Create or adapt:

- Contact
- Book demo
- Waitlist or start trial
- Features
- Pricing
- About
- Security
- Privacy
- Terms if launch-ready
- Case studies or resources if the product has proof
- Partner, reseller, or affiliate pages if growth motion needs them

## SEO And Metadata

Update:

- title template
- description
- canonical URL
- Open Graph image
- Twitter card
- structured data
- sitemap
- robots
- keywords
- organization schema
- app/software schema

Search and remove old brand/domain references before finalizing.
